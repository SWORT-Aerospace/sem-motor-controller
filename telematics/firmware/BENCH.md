# First bench: NUCLEO-U575ZI-Q telematics firmware

Generated by `tools/telematics_bench.py` from `telematics/bench/bench.yaml`; do not edit. `render --check` in CI fails if this page no longer matches the firmware, the BOM or the measured recording durations.

**Status: built and host-tested, never run on hardware.** No connection below has been made or measured; every row is unverified until a filled results form (from the bench package) says otherwise. Host tests run the portable C code and model the storage; they do not exercise the U575's peripherals.

**Power.** USB only, from the PC through the board's ST-LINK port. Nothing on this bench is connected to the vehicle, its battery or the controller's bus. The vehicle power connection is blocked (docs/TELEMATICS_BOM.md, section Vehicle supply).

Start with the minimal bench ([`BENCH_MINIMAL.md`](BENCH_MINIMAL.md)): one wheel input through the whole chain to a plot, and the document checks due before each step of either bench.

## 2. Build and package

```
# portable library, unit tests and host simulator
cmake -S telematics/firmware -B build-telematics -G Ninja
cmake --build build-telematics && ctest --test-dir build-telematics --output-on-failure

# target images (arm-none-eabi-gcc 13.2, Ubuntu 24.04 package gcc-arm-none-eabi)
cmake -S telematics/firmware -B build-u575 -G Ninja -DCMAKE_BUILD_TYPE=MinSizeRel \
      -DCMAKE_TOOLCHAIN_FILE=$PWD/telematics/firmware/cmake/arm-none-eabi-cortex-m33.cmake -DTM_TARGET_U575=ON
cmake --build build-u575

# the bench package: images, SHA-256 manifest, this procedure, parts, blank results form
python3 tools/telematics_bench.py package --images build-u575 --out build/telematics_bench --rebuild
```

The revision printed in the banner is `git describe --always --dirty` at configure time; the package refuses images whose revision differs from the tree or ends in `-dirty` (unless `--allow-dirty`, which marks it not valid for a recorded run). `--rebuild` builds the images again in a new directory and records whether every hash is equal.

| Use | Command |

| export programmer | `STM32_Programmer_CLI -c port=SWD freq=8000 -r 0x08100000 0x100000 dump.bin     # internal flash only (the NOR is not memory-mapped)` |

| status | `python3 tools/telematics_import.py --status-capture capture_B<n>.txt --out bench/B<n>` |

**Do not mass-erase: on internal storage that also erases the log. ERASE YES on the console clears the log on purpose.**

## 6. Procedure

Steps in order; each step's capture file is named `capture_B<n>.txt`. Write every measured value on the results form, including the ones that pass.

### B0. Preflight, unpowered

- **Do.** Wire every row of the connection table except can_* (the CAN Pal is added in B11); the IMU and TMP117 stay connected from here on. Board unplugged. Check every row of the connection table with the multimeter's continuity test and write the position of each "locate" pin on the form. Check that nothing above 3.3 V can reach an MCU pin and that 3V3 and 5V are not shorted to GND. Check the image hashes against MANIFEST.json (commands.verify).
- **Expect.** continuity on every row; no short; hashes equal
- **Record.** positions of PD0 and PD1; CAN Pal pin labels; continuity per row; hash of tm_u575.bin; hash of tm_u575_can.bin; hash of tm_u575_vehicle.bin.

### B1. Flash and start

- **Do.** Flash tm_u575.bin (commands.flash_*), open the console with capture (commands.console).
- **Expect.** Banner: "telematics tm_u575 <revision>" with the revision in MANIFEST.json (not ending in -dirty), "boot=1", "clock: TIM2 1 MHz from MSIS 4 MHz, PLL mode on the LSE (LSE accuracy)" (if the LSE starts), "log: W25Q NOR on SPI1 (JEDEC ef 40 18, 16384 KiB, 4096 slots), slot 0 of 4096", "IMU: ISM330DHCX, TMP117: 0x48", "chip: rev 0x...., fault record ..."; then one status line per second ("TM t=... tov=0 ... wheel=NNN ... log=full ..."); LD1 toggling every second.
- **Record.** banner text; LSE started yes/no; storage line; IMU and TMP117 line; silicon revision and fault-record line (for the errata and the SRAM_RST option).
- **Firmware text checked.** `main_u575.c`: "PLL mode on the LSE (LSE accuracy)"; `main_u575.c`: "W25Q NOR on SPI1 (JEDEC %02x %02x %02x, %lu KiB, %lu slots)"; `main_u575.c`: "IMU: %s, TMP117: %s"; `main_u575.c`: "chip: rev 0x%04x, fault record %s"; `tm_app.c`: "slots=%lu/%lu log=%s left=%ss thin=%lu"

### B2. Restarts and the watchdog

- **Do.** Press the reset button twice. Then halt the core for 5 s with the debugger (commands.halt): the main loop stops refreshing the watchdog.
- **Expect.** boot=2, then boot=3, with reset cause PIN for the button; after the halt, about 2 s into it, boot=4 with reset cause IWDG (the watchdog keeps counting while the core is halted, DC18). A board that stays halted for the 5 s and resumes without a restart fails this step: the watchdog would not catch a hung main loop either.
- **Record.** the four reset causes; whether the board restarted during the halt.
- **Firmware text checked.** `tm_reset.c`: "{TM_RST_IWDG, "IWDG"}"

### B3. One wheel channel at 100 Hz

- **Do.** 100.0 Hz square wave, 0 to 3.3 V, into wheel_0 (PA3) for 60 s, then stop. Keep capturing.
- **Expect.** edges= of wheel_0 rising by 100 per status line (plus or minus 1); within about 1 s "wheel=MII" (wheel_1 and wheel_2 are open: suspect inactive, as a disconnected sensor must read); after the stop "wheel=SNN".
- **Record.** generator model and its frequency accuracy; edges per second; wheel states.
- **Firmware text checked.** `tm_wheel.h`: "TM_WHEEL_SUSPECT_INACTIVE = 'I'"

### B4. Read the log back and import

- **Do.** DUMP on the console (still capturing), then commands.import with --wheel-circumference 0.1 (0.1 m per edge: 100 Hz reads 10.0 m/s, inside the 0 to 60 m/s plausibility range).
- **Expect.** wheel_0 speed 10.000 m/s while the generator ran, the deviation within the generator's accuracy plus 0.1 % (PROVISIONAL: 1 us capture over 100 ms is 10 ppm; the LSE-trimmed timebase is expected at ppm level, the untrimmed MSI is not characterised here); distance = edges x 0.1 m; after the stop "no_evidence", never 0; wheel_1 and wheel_2 speed "invalid" ("suspect: ... disconnected") while wheel_0 ran.
- **Record.** mean speed and its deviation; distance against edges; validity counts per channel; the speed plot; the commands.chain result (C2 and C5 to C7 with --pulse-hz 100 --circumference 0.1) and the commands.query listing (the stop shows as UNKNOWN; never as 0).

### B5. Rates

- **Do.** 1 Hz, 10 Hz, 1 kHz and 5 kHz into wheel_0, 20 s each; import with --wheel-circumference 0.01 (1 kHz reads 10 m/s).
- **Expect.** edges exactly 20 x the rate (plus or minus 1) at each; lost=0 at 1 Hz to 1 kHz
- **Record.** edge counts per rate; the rate at which lost= first rises; if any.

### B6. Stuck and disconnected sensor against a moving wheel

- **Do.** Feed the 10 Hz square wave to wheel_0 and wheel_1 together. (a) Pull wheel_1's lead off the generator for 5 s (the pull-up holds the line high), then reconnect it. (b) Pull the lead off again and jumper wheel_1 to GND for 5 s (stuck low: a short or a failed sensor; never jumper a line the generator drives), then remove the jumper and reconnect the lead. (c) Pull the lead off, jumper wheel_1 to GND, and stop the generator for 10 s.
- **Expect.** Both turning: "wheel=MMI" (wheel_2 open). (a) within about 1 s "wheel=MII", COUNTERS2 wheel_suspect_inactive +1, back to MMI on reconnection. (b) within about 1 s "wheel=MAI", wheel_suspect_active +1. (c) "wheel=SSN": a held line is not standstill. Import (--wheel-circumference 0.1): wheel_1 speed "invalid" with "stuck inactive or disconnected" in (a) and "stuck active" in (b), "no_evidence" in (c); no speed of 0 anywhere; wheel_1's distance a lower bound after (a).
- **Record.** status line at each change; the import's validity per interval; the two counters.
- **Firmware text checked.** `wheel.py`: "stuck inactive or "; `wheel.py`: "(stuck active: short to "; `stlg.py`: "wheel_suspect_inactive"; `stlg.py`: "wheel_suspect_active"

### B7. 75 minutes across the 32-bit timer overflow

- **Do.** With the NOR fitted (banner shows it), press reset (the 32-bit timer starts at 0), 1 kHz into wheel_0 for 75 min, capturing the console to one file. Then commands.status on the capture. It prints the slots= value n on the status line where tov= changes from 0 to 1 (4294.967 s after the reset); DUMP n-15 n+15 and import that capture with --wheel-circumference 0.01. A full DUMP is not needed (at 115200 baud a slot takes about 0.7 s to print).
- **Expect.** Status check PASS: t= continuous, tov 0 to 1 once, 4294.967 s after the reset, the edge rate steady at 1000 Hz on both sides. Log: wheel_0 speed 10.00 m/s in every record, including the one that spans the overflow; no record time jumps. left= after 2 min about 5804 s with the IMU and TMP117 connected (8292 s without), less the time earlier steps used: over the 4500 s of the step either way. Without the NOR (internal flash only) the log switches to sparse logging after about 5.3 min (7.6 min without the IMU and TMP117) and still holds the overflow, in records 10 s apart (docs/generated/telematics_storage.md).
- **Record.** status check output; the slot n at the overflow; speed around 4295 s; left= after 2 min.
- **Firmware text checked.** `telematics_import.py`: "DUMP {max(0, c['slot'] - 15)} {c['slot'] + 15}"

### B8. Power cut during a write

- **Do.** 100 Hz into wheel_0. Pull the USB cable while LD2 is on (a block waiting or being written); reconnect; DUMP and import.
- **Expect.** the next boot number and a power-related reset cause; at most one corrupt slot counted; nothing else lost before the last counters record
- **Record.** reset cause; the import's corrupt-slot count and accounting.

### B9. Internal flash fills; sparse logging

- **Do.** Pull the /CS wire off D10 (the 10 kOhm keeps the NOR deselected; its VCC stays connected, since an unpowered NOR can be fed through its driven inputs), reset, feed 100 Hz into wheel_0 with the IMU and TMP117 connected, and watch the status line.
- **Expect.** Banner "log: internal flash bank 2 (0x08100000, 1 MiB, 256 slots): no W25Q NOR of 1 to 16 MiB answered". log=full, then log=sparse after about 5.3 min (7.6 min without the IMU and TMP117), less if the internal log already holds sessions; thin= rising; an EVENT record (code 2) in the log.
- **Record.** time of the switch; thin= rate.
- **Firmware text checked.** `main_u575.c`: "internal flash bank 2 (0x08100000, 1 MiB, 256 slots): no W25Q NOR of 1 to 16 MiB answered"; `tm_app.c`: "sparse logging: storage reserve reached"

### B10. Erase

- **Do.** Put the /CS wire back on D10, reset, then ERASE YES.
- **Expect.** ERASING ..., a chip erase (up to a few minutes), restart, "slot 0 of 4096"
- **Record.** erase time.
- **Firmware text checked.** `main_u575.c`: "ERASING the log storage, then restarting"

### B11. CAN receive, receive-only

- **Do.** Board unplugged: wire the can_* rows. Bench bus: two jumper wires on the breadboard from the CAN Pal's CANH and CANL terminals to the first USB-CAN adapter; CAN Pal termination switch on (one end), the 120 Ohm across CANH-CANL at the adapter (the other end; adapter termination off); the multimeter reads about 60 Ohm across CANH-CANL unpowered. Flash tm_u575_can.bin. First the adapter alone sending 8-byte classic frames at 500 kbit/s; then add the second adapter, in normal (acknowledging) mode, on the same two wires.
- **Expect.** Banner "CAN: on (bus monitoring, 500 kbit/s classic)". Adapter alone: every frame ends in an acknowledge error at the adapter (nobody acknowledges: the board sends no acknowledge bit). With the second adapter: can= counts every frame and no frame from the board appears on the bus. The board's TX line stays high on the scope.
- **Record.** frame counts on every node; adapter error counters; scope trace of TX.
- **Firmware text checked.** `can_u575.c`: "on (bus monitoring, 500 kbit/s classic)"

### B12. IMU and temperature

- **Do.** tm_u575.bin with the IMU and TMP117 connected; 60 s at rest; DUMP and import.
- **Expect.** IMU records at about 100 Hz; TMP117 at 1 Hz within the sensor's accuracy of a reference thermometer
- **Record.** IMU axes against the board orientation; temperature against the reference.

### B13. GNSS receiver and PPS (tm_u575_vehicle)

- **Do.** Board unplugged: wire the gnss_* rows (the GNSS board and antenna are configuration A's lines gnss and gnss_antenna; the antenna by a window or outdoors). Flash tm_u575_vehicle.bin, capture the console for 15 min from a cold start of the receiver with the board at rest, probe PA1 with the scope, then DUMP and import.
- **Expect.** Banner "GNSS: USART2 PD6/PD5 38400 baud, UBX-NAV-PVT every 100 ms requested; PPS on PA1 (TIM2_CH2)". ## 7. Electrical checks before any vehicle bus

Before the unit goes near the controller team's bus (docs/CONTROLLER_INTERFACE_REQUEST.md section 5). Receive-only firmware does not by itself prove that the unit cannot disturb the bus; these checks are about the hardware. Legitimate traffic drives the shared bus dominant, so no check asks the bus to stay recessive while others send: each one tests what our node itself does.

| Check | Method | Pass |
|---|---|---|
| E1 Our transmitter is disabled in hardware | (a) Isolated bus, no other node: CAN Pal alone on a bench bus terminated at both ends (about 60 ohm), SLNT high, powered from the running board. Take the TX wire off PD1 (never short a driven MCU output) and force the CAN Pal's TX input low with a jumper to GND, then high to 3V3. Then, as a control, SLNT low with TX low. Put the TX wire back on PD1. (b) With traffic: one USB-CAN adapter sending frames that only our node could acknowledge. (c) A second, acknowledging adapter added. | (a) With SLNT high, CANH-CANL stays recessive (below 0.5 V) whatever TX does; with SLNT low and TX low it goes dominant (the control shows the measurement can see a dominant level). (b) Every frame ends in an acknowledge error at the sender, and the board's TX stays high: no dominant bit comes from our node. (c) The adapters' error counters do not change between 10,000 frames with and 10,000 without our node connected. |
| E2 Unpowered behaviour | unit unpowered, bus active with two acknowledging nodes | no change in the bus's error counters or waveform; the transceiver's unpowered leakage within its data sheet figure |
| E3 Termination | CANH-CANL resistance with the bus unpowered, with and without the unit | the unit adds no termination (the CAN Pal's switch off) unless the interface agreement asks for it; about 60 ohm for a bus terminated at both ends |
| E4 Bus loading | the unit's input capacitance (transceiver data sheet) and its stub length | stub within the limit agreed with the controller team for their bit rate |
| E5 Ground | the unit's ground reference to the controller's CAN ground | one ground connection at the agreed point; no ground loop through a USB-connected PC on the vehicle |
| E6 Supply | the unit's own supply | blocked: no vehicle supply until V_bat,max is known and the supply parts are selected (docs/TELEMATICS_BOM.md); the unit never takes power from the controller's connector |

Step B11 shows receive-only behaviour at the protocol level; E1 to E6 are about the hardware.
